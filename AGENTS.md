# AGENTS.md

## Project
DocFlow (Vordruckwerk) — self-hosted PDF form-filling engine. Next.js 16 App Router, TypeScript strict, React 19, Tailwind CSS 4 (dark theme). Single Docker container, file-based persistence. UI text in German, code/comments in English.

Two halves of the app share the same field model but are separate directory trees:
- `components/editor/` — admin template designer. `TemplateEditor.tsx` is the orchestrator (zoom/scroll state incl. click/drag-to-zoom, tool selection, save/discard, keyboard shortcuts) and composes `PdfPageView.tsx` (canvas + drag/resize/marquee-select/region-drag tools), `Inspector.tsx` (per-field property panel, including the formula editor), `FieldListPanel.tsx`, `AlignToolbar.tsx` (align/distribute/link, shown on multi-select).
- `components/fill/` — end-user fill form. `FillForm.tsx` (values, drafts, date-series, semantic timesheet grouping) + `PagePreview.tsx` (read-only live preview).

## Commands
- Dev: `npm run dev` (:3000). Requires `.env` (or env vars): `AUTH_SECRET` (≥32 chars), optional `DATA_DIR`.
- Typecheck (fast, use before every non-trivial change): `npx tsc --noEmit`.
- Build: `npm run build` → standalone output (`output: "standalone"` for Docker). Needs `AUTH_SECRET` set in the shell (e.g. `$env:AUTH_SECRET="..."`) or it fails at build-time page collection, not just at request time.
- Tests (manual smoke): boot dev server, or `node .next/standalone/server.js` after build. (No unit-test framework pinned yet.)
- CI (`.github/workflows/pr-ci.yml`): on every push/PR to `main` it runs `npm ci && npm run build`. On push to `main` (or manual `workflow_dispatch`) a second job **builds and pushes a Docker image to Docker Hub** (`docflow:latest` + `:<sha>`) using `DOCKER_USERNAME`/`DOCKER_PASSWORD` secrets. Pushing to `main` is a real release, not just a cosmetic sync — confirm with the user before `git push`.

## Conventions
- `lib/types.ts` is the single source of truth for the domain model (`TemplateField`, `StoredTemplate`, `Store`, etc.).
- Persistence: `$DATA_DIR/store.json` (single JSON blob, serialized writes via `lib/store.ts#withStore`) + `$DATA_DIR/templates/<uuid>.pdf`. Never commit `data/`.
- Auth: password scrypt (`scrypt:salt:hash`), sessions = HMAC token cookie `vw_session` (7d). Secret from `AUTH_SECRET`; fails loudly at request time, never at build time.
- All API routes: Route Handlers, `export const runtime = "nodejs"`, German errors `{ error: "..." }` via `lib/api.ts` (`jsonError`/`jsonErrorFor`/`parseJsonBody`).
- Field coordinates: PDF points, TOP-LEFT origin, always in **un-rotated media-box space** even when `pageRotations` is set. `lib/pdf/fill.ts` (server export) and `components/PreviewSvg.tsx` (editor overlay + fill-form preview) render the exact same field, so any text-placement change must update **both**, using the shared math in `lib/geometry.ts` (`baselineFromTop`, `textAlignX`, `fitSingleLine`, `fitMultiline`, `multilineFirstBaseline`, matrix helpers). Server measures text via pdf-lib `font.widthOfTextAtSize`; browser measures via `lib/pdf/client.ts#measureText`/`wrapClient` (canvas 2D context) — keep the `measure` fn signature `(text, size) => width` identical on both sides.
- `TemplateField.linkKey`: fields sharing a `linkKey` collapse into one input in the fill form (`FillForm.tsx#groupFields`); create/remove links from the editor's `AlignToolbar` (shown on 2+ field selection). Legacy fallback: fields with identical `label`+`kind` and no `linkKey` also group.
- `StoredTemplate.pageRotations[page]` (`0|90|180|270`): server rotates via `page.setRotation(degrees(rot))` in `fill.ts` (pdf-lib rotates background + drawn content together, so field coords never change). Previews replicate this visually by wrapping canvas+SVG in a CSS-rotated `<div>` centered inside an outer box sized to the *display* (width/height swapped for 90/270) — see `PdfPageView.tsx`/`PagePreview.tsx`. The editor's pointer→field-coordinate math (`toPt` in `PdfPageView.tsx`) must inverse-rotate screen coords back to media space.
- pdfjs-dist v6: `getDocument({ url })`, `page.render({ canvas, viewport })`; worker in `public/` (postinstall script `scripts/copy-pdf-worker.mjs`). Load pdfjs only via `lib/pdf/client.ts`.
- Drafts are server-side, not `localStorage`: `Store.savedFills` + `/api/fills` routes. One reserved auto-draft per user+template (`auto: true`, debounced ~800ms save from `FillForm.tsx`) plus named drafts the user can select and overwrite.
- `lib/formula.ts`: Excel-like formula engine for computed, read-only fields (`TemplateField.formula`, available on `text`/`multiline` kinds) — hand-written tokenizer + recursive-descent parser, no `eval`. Supports `+ - * / %`, comparisons (`= <> < <= > >=`), and `SUM MIN MAX AVG ABS ROUND ROUNDUP ROUNDDOWN CEIL FLOOR MOD IF AND OR NOT`; formulas can reference other formula fields (chaining). `evaluateFormulas` is the authoritative evaluator (used by both the fill form and `lib/pdf/fill.ts` at export time) and silently degrades a broken formula to `"#FEHLER"`; `previewFormula` is a separate, non-swallowing variant used only by `Inspector.tsx`'s live preview to surface the actual parser error while editing. `,` is both the German decimal separator and the argument separator — a bare `N,N` is genuinely ambiguous and resolves in favor of the decimal (tokenizer only treats `,` as decimal when a digit immediately follows); use a space after the comma or `;` to write two adjacent numeric arguments unambiguously.
- `lib/editor-utils.ts#parseImportedFields`: powers the editor's "📥 JSON importieren" button — takes arbitrary JSON (`TemplateField[]`-shaped or `{ "fields": [...] }`), keeps only entries with valid `label`/`kind`/`x`/`y`/`width`/`height`, defaults everything else, clamps `page` into range, and always regenerates `id` (imported ids are never trusted). Returns `{ fields, errors }` — valid fields are appended to the in-editor `fields` state (marks the template dirty; still requires "Speichern" to persist) and per-entry `errors` are surfaced to the admin instead of silently dropped. This is the intended handoff point for a field layout worked out externally (e.g. Claude pixel-scanning a blank PDF to produce exact coordinates) without needing per-field manual placement or direct API calls.
- Multi-week/multi-shift documents (e.g. a duplex Früh-/Spätschicht sheet, one KW box + one week of Datum fields per page): `FillForm.tsx#dateGroupsByPage` splits date fields by page and renders one independent `DateSeriesPanel` per qualifying page instead of one shared picker for the whole document. Both that panel's default Woche/KW guess and the KW digit-box fields (`defaultKwValues`) number pages one week apart via `weekOffsetForRank`, and both respect a `swapWeeks` toggle (persisted to `localStorage` per template — read in an effect after mount, never in the lazy `useState` initializer, per the footgun below) for when an alternating rotation happens to have the earlier page as next week's shift instead of this week's. `StoredTemplate.autoCurrentWeek` ("Tätigkeitsnachweis-Modus", toggled in the editor toolbar's "Modus" group) makes the KW boxes *and* date fields always re-derive from today's date on load — overriding a saved draft's stale values on purpose — instead of the normal default-only-as-fallback behavior.
- Page repetition ("Endlos-Modus") comes in two independent flavors sharing one core, `lib/editor-utils.ts#expandFieldsForRepeat` + `lib/pdf/expand.ts#expandPdfPages`/`repeatPerPage`: appends `times` more copies of a page set's *entire current page set* to both the PDF (pdf-lib `copyPages`/`addPage`, same document as source and destination) and the field list, so a 2-page duplex sheet becomes 4/6/8/… pages for a longer recurring run. Copied fields keep their page-rank-based day/column labels working unmodified (KW/date numbering is purely rank-based, see above) but get a `(2)`, `(3)`, … suffix per block via `uniqueCopyLabel` unless they already carry a `linkKey` (e.g. Name/Vorname), which is left untouched so those stay one shared input across every block.
  - **Permanent** (`app/api/templates/[id]/repeat-pages/route.ts`, admin-only): actually rewrites the stored template — real use case is "this template should just be 8 pages from now on." Its undo is `trim-pages` ("✂️ auf N kürzen") — cuts the PDF/field list back to the first N pages; it's specifically repeat-pages' inverse (trim from the end), not a general page-delete tool.
  - **Temporary** (the "Endlos-Modus" panel on `FillForm.tsx`, next to the download button, open to any filler): "how many weeks to print" as a per-export choice that never touches the saved template. `weekBlocks` (local state, default 1) drives `effectiveFields`/`effectivePageCount` — every place that used to read `template.fields`/`template.pageCount` directly (groups, pageGroups, computedValues, the KW/date defaults, the `PagePreview` loop) reads these instead. `expandFieldsForRepeat` generates **deterministic** ids (`` `${originalId}::rep${block}` ``, not `newFieldId()`'s random UUIDs) specifically so this works: the browser expands the field list to build its own `values` state, and separately, `POST /api/fill` (given the same `templateId` + `weekBlocks`) *independently* re-derives the identical expanded field list server-side to know what to fill — neither side ever sends the other its field list, so the ids must land on their own. Preview pages beyond the real PDF's page count map back via `pageIndex % template.pageCount` for the canvas render (the file on disk is never touched) while still using the correctly-page-shifted virtual field's coordinates for the SVG overlay.
- `PdfPageView.tsx` field labels float ~20 screen px above their box; on a densely-packed grid (e.g. a day-by-day timesheet row) that label rectangle collides with whatever field sits directly above it, and the fields in the middle of a tall stack end up permanently buried under other rows' labels regardless of zoom. `crampedIds` (a `useMemo` doing real AABB collision detection between every field's label rectangle and every other field's box, not just a flat zoom or self-height cutoff — an isolated field of the same height, e.g. Name/Vorname with nothing above it, must still always show its label) hides the label for any field it flags, showing it again on hover or selection via `hoveredId`. A linked field's colored dot is rendered separately, anchored inside the field's own box corner (not floating in the label above it), so it stays visible even when the label is hidden — it used to live inside the (sometimes-hidden) label span.
- `app/fill/[id]/page.tsx` hand-picks which `StoredTemplate` properties reach `FillForm` (server component, not a raw passthrough) — it previously used `as StoredTemplate` to paper over missing properties; it's `satisfies StoredTemplate` now so the compiler catches the next one. Adding a new `StoredTemplate` field that the fill form needs means adding it here too, or it silently reads as `undefined` on the fill page despite being present on the template everywhere else (bit us once with `pageRotations` and `autoCurrentWeek`).
- An effect with a narrow dependency array (e.g. `[template.id]`, so it only fetches once) that reads other state inside its async callback closes over that state's value *from whenever the effect was defined* — not its value when the callback actually runs. If that state can change before the async work resolves, mirror it into a ref (updated by its own tiny effect) and read `ref.current` inside the callback instead of the state variable directly. Hit this with the auto-draft-load effect: it read `swapWeeks` directly, so on every fresh page load it silently reverted the week swap back to unswapped once the (slower) drafts fetch resolved after the (faster) localStorage-restore effect had already toggled it.
- React 19 gotchas: no `ref.current` writes during render; no sync `setState` in effect bodies; cancel previous `page.render()` tasks before re-render (StrictMode-safe).
- Sticky UI: app navbar is `top-0 z-40`; page toolbars stick at `top-16`.
- Email (nodemailer) is best-effort: log errors, never block downloads.

## Known footguns (already hit in this repo — don't reintroduce)
- Never read `localStorage`/`window` inside a `useState(() => …)` lazy initializer in `components/fill/*` or `components/editor/*` — these are client components rendered under SSR, so the lazy initializer runs on the server too, producing empty state that mismatches the client's hydrated state. Load such data in a `useEffect` after mount instead.
- Never gate a `<canvas>`'s mount on state that is only set by measuring that same canvas via its ref — the canvas then never mounts, the measurement effect never runs, and the state never updates (permanent blank render). Always mount the canvas unconditionally and gate overlays/siblings around it.
- Never rely on a scrollable container's `clientHeight`/`clientWidth` for "available viewport space" unless that container has a real CSS-imposed height/width (from its own ancestry, not from its own content) — a `flex`/block box that only auto-sizes to its children reports its *content's current size* back, not the true viewport, which silently breaks any "fit to screen" math (each recompute just measures its own last output). `TemplateEditor.tsx`'s stage binds its height explicitly (via `getBoundingClientRect` + a `ResizeObserver` on the toolbar) for exactly this reason.
- Never put `justify-content: center` (or `align-items: center`) on a `overflow-auto` flex/grid container that can hold content wider/taller than itself — this is a well-known cross-browser trap: once content overflows, the browser only lets you scroll into part of the overflow and `scrollWidth`/`scrollHeight` under-report the true content size, silently corrupting any "scroll to a computed position" logic. Center via `margin: auto` on the child instead (see the stage in `TemplateEditor.tsx`).
- Never write `el.scrollLeft`/`el.scrollTop` synchronously right after a state update that will resize `el`'s scrollable content (e.g. a zoom-level change) — the write lands before React/the DOM has actually resized, so it's silently clamped to the *old* (pre-resize) scrollable range. Stage the target position (e.g. in a ref) and apply it from a `useLayoutEffect` keyed on the state that drives the resize, so it runs after the DOM has already grown/shrunk.
- When canceling a `pdf.js` `RenderTask` (`.cancel()`) before ever awaiting its `.promise`, still attach a `.catch(() => {})` to that promise — `.cancel()` rejects it with `RenderingCancelledException`, and if nothing else is awaiting/catching it, it surfaces as an unhandled promise rejection (crashes the Next.js dev overlay) every time a render gets superseded before it starts, e.g. on mount when auto-fit-to-screen changes the zoom right after the first render kicked off.
