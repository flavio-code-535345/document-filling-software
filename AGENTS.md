# AGENTS.md

## Project
DocFlow (Vordruckwerk) — self-hosted PDF form-filling engine. Next.js 16 App Router, TypeScript strict, React 19, Tailwind CSS 4 (dark theme). Single Docker container, file-based persistence. UI text in German, code/comments in English.

Two halves of the app share the same field model but are separate directory trees:
- `components/editor/` — admin template designer. `TemplateEditor.tsx` is the orchestrator (zoom/scroll state incl. click/drag-to-zoom, tool selection, save/discard, keyboard shortcuts) and composes `PdfPageView.tsx` (canvas + drag/resize/marquee-select/region-drag tools), `Inspector.tsx` (per-field property panel, including the formula editor), `FieldListPanel.tsx`, `AlignToolbar.tsx` (align/distribute/link, shown on multi-select).
- `components/fill/` — end-user fill form. `FillForm.tsx` (values, drafts, date-series, semantic timesheet grouping) + `PagePreview.tsx` (read-only live preview).

## Commands
- Dev: `npm run dev` (:3000). Requires `.env` (or env vars): `AUTH_SECRET` (≥32 chars), optional `DATA_DIR`.
- Typecheck (fast, use before every non-trivial change): `npx tsc --noEmit`.
- Build: `npm run build` → standalone output (`output: "standalone"` for Docker). Needs `AUTH_SECRET` set in the shell (e.g. `$env:AUTH_SECRET="..."`) or it fails at build-time page collection, not just at request time.
- Tests (manual smoke): boot dev server, or `node .next/standalone/server.js` after build. (No unit-test framework pinned yet.)
- CI (`.github/workflows/pr-ci.yml`): on every push/PR to `main` it runs `npm ci && npm run build`. On push to `main` (or manual `workflow_dispatch`) a second job **builds and pushes a Docker image to Docker Hub** (`docflow:latest` + `:<sha>`) using `DOCKER_USERNAME`/`DOCKER_PASSWORD` secrets. Pushing to `main` is a real release, not just a cosmetic sync — confirm with the user before `git push`.

## Conventions
- `lib/types.ts` is the single source of truth for the domain model (`TemplateField`, `StoredTemplate`, `Store`, etc.).
- Persistence: `$DATA_DIR/store.json` (single JSON blob, serialized writes via `lib/store.ts#withStore`) + `$DATA_DIR/templates/<uuid>.pdf`. Never commit `data/`.
- Auth: password scrypt (`scrypt:salt:hash`), sessions = HMAC token cookie `vw_session` (7d). Secret from `AUTH_SECRET`; fails loudly at request time, never at build time.
- All API routes: Route Handlers, `export const runtime = "nodejs"`, German errors `{ error: "..." }` via `lib/api.ts` (`jsonError`/`jsonErrorFor`/`parseJsonBody`).
- Field coordinates: PDF points, TOP-LEFT origin, always in **un-rotated media-box space** even when `pageRotations` is set. `lib/pdf/fill.ts` (server export) and `components/PreviewSvg.tsx` (editor overlay + fill-form preview) render the exact same field, so any text-placement change must update **both**, using the shared math in `lib/geometry.ts` (`baselineFromTop`, `textAlignX`, `fitSingleLine`, `fitMultiline`, `multilineFirstBaseline`, matrix helpers). Server measures text via pdf-lib `font.widthOfTextAtSize`; browser measures via `lib/pdf/client.ts#measureText`/`wrapClient` (canvas 2D context) — keep the `measure` fn signature `(text, size) => width` identical on both sides.
- `TemplateField.linkKey`: fields sharing a `linkKey` collapse into one input in the fill form (`FillForm.tsx#groupFields`); create/remove links from the editor's `AlignToolbar` (shown on 2+ field selection). Legacy fallback: fields with identical `label`+`kind` and no `linkKey` also group.
- `StoredTemplate.pageRotations[page]` (`0|90|180|270`): server rotates via `page.setRotation(degrees(rot))` in `fill.ts` (pdf-lib rotates background + drawn content together, so field coords never change). Previews replicate this visually by wrapping canvas+SVG in a CSS-rotated `<div>` centered inside an outer box sized to the *display* (width/height swapped for 90/270) — see `PdfPageView.tsx`/`PagePreview.tsx`. The editor's pointer→field-coordinate math (`toPt` in `PdfPageView.tsx`) must inverse-rotate screen coords back to media space.
- pdfjs-dist v6: `getDocument({ url })`, `page.render({ canvas, viewport })`; worker in `public/` (postinstall script `scripts/copy-pdf-worker.mjs`). Load pdfjs only via `lib/pdf/client.ts`.
- Drafts are server-side, not `localStorage`: `Store.savedFills` + `/api/fills` routes. One reserved auto-draft per user+template (`auto: true`, debounced ~800ms save from `FillForm.tsx`, entirely separate from and unaffected by the manual-draft UI below) plus named drafts the user can pick, load, and overwrite. The manual side is one `<select>` dropdown (not a row of chip buttons) plus explicit "Laden"/"Speichern"/"✕" buttons that act immediately on whichever draft the dropdown has picked (`activeDraftId`, `pickDraft`/`loadActiveDraft`/`saveDraft`/`deleteDraft` in `FillForm.tsx`) — picking an entry in the dropdown (`pickDraft`) only marks it as the current target and shows its name, it never touches the form's `values` by itself; only an explicit "Laden" click does that (`loadActiveDraft`). This split exists so browsing the dropdown to see what's saved can never silently clobber whatever's currently being filled in — the previous chip-based UI conflated "select" and "load" into one click. `saveDraft` also no longer clears `draftName`/`activeDraftId` after a successful save (an earlier version did, which read as "the draft I just picked vanished" even though the save itself worked and the dropdown still had it selected).
- `lib/formula.ts`: Excel-like formula engine for computed, read-only fields (`TemplateField.formula`, available on `text`/`multiline` kinds) — hand-written tokenizer + recursive-descent parser, no `eval`. Supports `+ - * / %`, comparisons (`= <> < <= > >=`), and `SUM MIN MAX AVG ABS ROUND ROUNDUP ROUNDDOWN CEIL FLOOR MOD IF AND OR NOT`; formulas can reference other formula fields (chaining). `evaluateFormulas` is the authoritative evaluator (used by both the fill form and `lib/pdf/fill.ts` at export time) and silently degrades a broken formula to `"#FEHLER"`; `previewFormula` is a separate, non-swallowing variant used only by `Inspector.tsx`'s live preview to surface the actual parser error while editing. `,` is both the German decimal separator and the argument separator — a bare `N,N` is genuinely ambiguous and resolves in favor of the decimal (tokenizer only treats `,` as decimal when a digit immediately follows); use a space after the comma or `;` to write two adjacent numeric arguments unambiguously.
- `lib/editor-utils.ts#parseImportedFields`: powers the editor's "📥 JSON importieren" button — takes arbitrary JSON (`TemplateField[]`-shaped or `{ "fields": [...] }`), keeps only entries with valid `label`/`kind`/`x`/`y`/`width`/`height`, defaults everything else, clamps `page` into range, and always regenerates `id` (imported ids are never trusted). Returns `{ fields, errors }` — valid fields are appended to the in-editor `fields` state (marks the template dirty; still requires "Speichern" to persist) and per-entry `errors` are surfaced to the admin instead of silently dropped. This is the intended handoff point for a field layout worked out externally (e.g. Claude pixel-scanning a blank PDF to produce exact coordinates) without needing per-field manual placement or direct API calls.
- Multi-week/multi-shift documents (e.g. a duplex Früh-/Spätschicht sheet, one KW box + one week of Datum fields per page): `FillForm.tsx#dateGroupsByPage` splits date fields by page and renders one independent `DateSeriesPanel` per qualifying page instead of one shared picker for the whole document. `weekPages`/`weekPageRank` (a page → 0-based-rank map, union of every page in `dateGroupsByPage` plus every page carrying at least one KW digit-box field) is the *one* shared ranking both the KW boxes and the Datumsreihe panels number pages from — `weekForRank(rank, groupSize, swap, anchor)` turns a page's rank into an actual ISO year/week relative to the anchor, and both `defaultKwValues` and `freshDateValues` call it per-page (never per-field): every KW field on the *same* page always gets the *same* week, even if a page carries more than one (e.g. a page with both a "Frühschicht KW" and a "Spätschicht KW" box for its one shared week). `StoredTemplate.autoCurrentWeek` ("Tätigkeitsnachweis-Modus", toggled in the editor toolbar's "Modus" group) makes the KW boxes *and* date fields always re-derive from the anchor on load, on swap/weekBlocks change, *and* on every anchor edit — overriding a saved draft's stale values on purpose — instead of the normal default-only-as-fallback behavior; a non-`autoCurrentWeek` template still gets this automatic re-derive for the KW boxes only (dates stay manual, via each panel's own "Anwenden"). The Datumsreihe panel's per-field checkbox selection (`seriesByPage` in `FillForm.tsx`, keyed by page) is lifted up out of `DateSeriesPanel` specifically so `freshDateValues` can see it too — a field unchecked there (e.g. "I don't work Saturdays") is explicitly cleared (not just skipped) by Tätigkeitsnachweis-Modus's automatic refresh instead of that refresh silently re-filling it on every swap/weekBlocks change regardless of the checkbox. `seriesByPage` is persisted to `localStorage` per template (`setPageSelection`, same restore-after-mount pattern as `swapWeeks` below) — "I don't work weekends" is a standing fact about how someone fills a given template, not a one-visit toggle, so it needs to survive a reload; it used to be plain in-memory state that silently reset to "everything included" on every fresh page load, which read as the exclusion never actually saving. Only non-null entries (pages where something's actually excluded) are written, so an untouched page doesn't bloat storage with an explicit "everything" the default already means. Note this is keyed by absolute page number, so it doesn't currently follow a page's Endlos-Modus block copies (Seite 1's exclusion doesn't automatically apply to Seite 3's block-2 copy of the same role) — each block's pages need their own exclusion set for now. Both `freshDateValues` and `DateSeriesPanel#applyWeek` compute the *full* week over every group first and only then filter/write by each group's own position, not the filtered subset's position — indexing off the filtered list instead would shift every later day's date by one slot whenever an excluded day sits in the middle of the week rather than trailing at the end.
- Exactly one page's Datumsreihe panel is ever the editable "anchor" at a time — its Jahr/KW is a real input, and every other page's is a disabled, derived display ("folgt Seite N") computed via the shared `weekForRank`. *Which* page that is moves with the `swapWeeks` toggle (`anchorPageRank` in `FillForm.tsx`: slot 0 unswapped, the last slot of the block when swapped) instead of always being panel 1 — this went through two designs before landing here, both from real admin feedback, and the reasoning matters for not regressing either fix:
  - **v1** (pre-anchor): every panel had independent local `year`/`week` state defaulting off *today* with zero coordination — editing one did nothing to the others, and the sequence across panels (and between panels and the printed KW boxes) drifted into an unrelated set of numbers.
  - **v2** (anchor fixed at panel 1): introduced the shared anchor, but kept the anchor slot hardcoded at rank 0 and modeled `swap` as reversing the *other* page's offset backward from it (`weekOffsetForRank` returning a negative relative offset for swapped non-anchor slots). Mathematically fine, but it read as nonsense to an admin: toggling swap made the anchor's own page look frozen (its offset-from-itself is always zero by construction, so a manually-typed anchor value never itself reacted to swap), and — worse — the pair it was inverting used a *different* window of weeks entirely (e.g. anchor stays 38, partner goes to 37, instead of just re-assigning {38, 39} between the two pages). An admin who needed the late shift to start at KW 38 had no way to get there: they could only type into panel 1, and swap only ever subtracted a week from the *other* page.
  - **v3** (current): `swap` instead picks which *slot* in the block is the anchor slot (`weekOffsetForRank`'s `anchorSlot`), and every non-anchor slot in the same block is always some whole number of weeks *forward* from it, counting cyclically (`(slot - anchorSlot + groupSize) % groupSize`, never negative). This means: (1) the anchor's own page is whichever page is currently in the anchor slot, so its typed value is never frozen against swap — swap simply relocates it to a different physical page, taking the admin's typed number with it (`anchorOverride` is deliberately *not* cleared on swap anymore, unlike v2 — the number's meaning doesn't change, only which page shows it); (2) a swapped pair always reuses the exact same pair of consecutive weeks as unswapped, just reassigned between the two pages (38/39 becomes 39/38, never 37/38) — "clean" in the sense an admin actually asked for. `weekForRank`'s result is already relative to the anchor (0 at the anchor's own rank), so there's no separate anchor-offset subtraction step left in `weekForRank`/`defaultKwValues`/`freshDateValues` — that entire class of "the anchor is defined as itself minus itself" footgun from v2 no longer exists. `defaultAnchor` (used only when no override is typed yet) is simply `isoWeekOf(new Date())` — today's actual week, full stop — since swap no longer needs to bias it; the anchor page defaulting to "this week" and every other page counting forward from it already reproduces the same real-world guess. `defaultKwValues`/`freshDateValues` still parse the anchor's live `year`/`week` strings defensively (`safeAnchor`, falling back to `defaultAnchor`) since they write straight into real field values — a momentarily-empty or out-of-range box while the admin is mid-edit must never get a chance to stamp `"NaN"` into every KW field in the document.
- Page repetition ("Endlos-Modus") comes in two independent flavors sharing one core, `lib/editor-utils.ts#expandFieldsForRepeat` + `lib/pdf/expand.ts#expandPdfPages`/`repeatPerPage`: appends `times` more copies of a page set's *entire current page set* to both the PDF (pdf-lib `copyPages`/`addPage`, same document as source and destination) and the field list, so a 2-page duplex sheet becomes 4/6/8/… pages for a longer recurring run. Copied fields keep their page-rank-based day/column labels working unmodified (KW/date numbering is purely rank-based, see above) but get a `(2)`, `(3)`, … suffix per block via `uniqueCopyLabel` unless they already carry a `linkKey` (e.g. Name/Vorname), which is left untouched so those stay one shared input across every block.
  - **Permanent** (`app/api/templates/[id]/repeat-pages/route.ts`, admin-only): actually rewrites the stored template — real use case is "this template should just be 8 pages from now on." Its undo is `trim-pages` ("✂️ auf N kürzen") — cuts the PDF/field list back to the first N pages; it's specifically repeat-pages' inverse (trim from the end), not a general page-delete tool.
  - **Temporary** (the "Endlos-Modus" control inside `FillForm.tsx`'s "Erweiterte Optionen" section, open to any filler): "how many weeks to print" as a per-export choice that never touches the saved template. `weekBlocks` (local state, default 1) drives `effectiveFields`/`effectivePageCount` — every place that used to read `template.fields`/`template.pageCount` directly (groups, pageGroups, computedValues, the KW/date defaults, the `PagePreview` loop) reads these instead. `expandFieldsForRepeat` generates **deterministic** ids (`` `${originalId}::rep${block}` ``, not `newFieldId()`'s random UUIDs) specifically so this works: the browser expands the field list to build its own `values` state, and separately, `POST /api/fill` (given the same `templateId` + `weekBlocks`) *independently* re-derives the identical expanded field list server-side to know what to fill — neither side ever sends the other its field list, so the ids must land on their own. Preview pages beyond the real PDF's page count map back via `pageIndex % template.pageCount` for the canvas render (the file on disk is never touched) while still using the correctly-page-shifted virtual field's coordinates for the SVG overlay. It's positioned *before* the per-page field sections (not after, near the download button) specifically so raising it doesn't reveal new "Seite N" sections above your current scroll position.
  - `expandFieldsForRepeat` also rewrites `{Label}` references inside a copied field's `formula`: a formula field (e.g. a "Total-Std" summing that week's day fields) is copied like any other field, but a formula's `{...}` tokens are plain label text — left untouched, every duplicated copy would keep computing from block 0's fields forever, invisible for as long as every block happens to hold the same numbers (e.g. right after filling in from `defaultValue`) but wrong the moment one block's values are edited independently of another's. The fix builds an old-label→new-label map for everything relabeled in that same block (skipping linked fields, which intentionally keep their label) and rewrites matching `{...}` tokens in every copy's formula to point at that block's own sibling instead.
- `PdfPageView.tsx` field labels float ~20 screen px above their box; on a densely-packed grid (e.g. a day-by-day timesheet row) that label rectangle collides with whatever field sits directly above it, and the fields in the middle of a tall stack end up permanently buried under other rows' labels regardless of zoom. `crampedIds` (a `useMemo` doing real AABB collision detection between every field's label rectangle and every other field's box, not just a flat zoom or self-height cutoff — an isolated field of the same height, e.g. Name/Vorname with nothing above it, must still always show its label) hides the label for any field it flags, showing it again on hover or selection via `hoveredId`. A linked field's colored dot is rendered separately, anchored inside the field's own box corner (not floating in the label above it), so it stays visible even when the label is hidden — it used to live inside the (sometimes-hidden) label span. That collision check is vertical-only (a field vs. the row above it) and doesn't catch a full row of adjacent narrow columns (e.g. Von/Bis/Pause/Stunden) bleeding *sideways* into each other — a long label like "Frühschicht Montag Pause" is routinely wider than its own column even with nothing directly above it. Handled separately: every label is CSS-capped to roughly its own field's rendered width (`overflow: hidden; text-overflow: ellipsis`) by default and only allowed to expand past that (`maxWidth: none`) while focused (hover/selected/multi-selected, via the same `isFocused` used for the vertical case) — same trade as the vertical fix, temporary overlap while deliberately inspecting one field beats permanent clutter across all of them.
- `app/fill/[id]/page.tsx` hand-picks which `StoredTemplate` properties reach `FillForm` (server component, not a raw passthrough) — it previously used `as StoredTemplate` to paper over missing properties; it's `satisfies StoredTemplate` now so the compiler catches the next one. Adding a new `StoredTemplate` field that the fill form needs means adding it here too, or it silently reads as `undefined` on the fill page despite being present on the template everywhere else (bit us once with `pageRotations` and `autoCurrentWeek`).
- An effect with a narrow dependency array (e.g. `[template.id]`, so it only fetches once) that reads other state inside its async callback closes over that state's value *from whenever the effect was defined* — not its value when the callback actually runs. If that state can change before the async work resolves, mirror it into a ref (updated by its own tiny effect) and read `ref.current` inside the callback instead of the state variable directly. Hit this with the auto-draft-load effect: it read `swapWeeks` directly, so on every fresh page load it silently reverted the week swap back to unswapped once the (slower) drafts fetch resolved after the (faster) localStorage-restore effect had already toggled it.
- React 19 gotchas: no `ref.current` writes during render; no sync `setState` in effect bodies; cancel previous `page.render()` tasks before re-render (StrictMode-safe).
- Sticky UI: app navbar is `top-0 z-40`; page toolbars stick at `top-16`.
- Email (nodemailer) is best-effort: log errors, never block downloads.

## Known footguns (already hit in this repo — don't reintroduce)
- Never read `localStorage`/`window` inside a `useState(() => …)` lazy initializer in `components/fill/*` or `components/editor/*` — these are client components rendered under SSR, so the lazy initializer runs on the server too, producing empty state that mismatches the client's hydrated state. Load such data in a `useEffect` after mount instead.
- Never gate a `<canvas>`'s mount on state that is only set by measuring that same canvas via its ref — the canvas then never mounts, the measurement effect never runs, and the state never updates (permanent blank render). Always mount the canvas unconditionally and gate overlays/siblings around it.
- Never rely on a scrollable container's `clientHeight`/`clientWidth` for "available viewport space" unless that container has a real CSS-imposed height/width (from its own ancestry, not from its own content) — a `flex`/block box that only auto-sizes to its children reports its *content's current size* back, not the true viewport, which silently breaks any "fit to screen" math (each recompute just measures its own last output). `TemplateEditor.tsx`'s stage binds its height explicitly (via `getBoundingClientRect` + a `ResizeObserver` on the toolbar) for exactly this reason.
- Never put `justify-content: center` (or `align-items: center`) on a `overflow-auto` flex/grid container that can hold content wider/taller than itself — this is a well-known cross-browser trap: once content overflows, the browser only lets you scroll into part of the overflow and `scrollWidth`/`scrollHeight` under-report the true content size, silently corrupting any "scroll to a computed position" logic. Center via `margin: auto` on the child instead (see the stage in `TemplateEditor.tsx`).
- Never write `el.scrollLeft`/`el.scrollTop` synchronously right after a state update that will resize `el`'s scrollable content (e.g. a zoom-level change) — the write lands before React/the DOM has actually resized, so it's silently clamped to the *old* (pre-resize) scrollable range. Stage the target position (e.g. in a ref) and apply it from a `useLayoutEffect` keyed on the state that drives the resize, so it runs after the DOM has already grown/shrunk.
- When canceling a `pdf.js` `RenderTask` (`.cancel()`) before ever awaiting its `.promise`, still attach a `.catch(() => {})` to that promise — `.cancel()` rejects it with `RenderingCancelledException`, and if nothing else is awaiting/catching it, it surfaces as an unhandled promise rejection (crashes the Next.js dev overlay) every time a render gets superseded before it starts, e.g. on mount when auto-fit-to-screen changes the zoom right after the first render kicked off.
